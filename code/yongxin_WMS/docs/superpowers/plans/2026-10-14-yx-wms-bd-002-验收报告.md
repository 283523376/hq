## 2. 端到端实测（真库、真服务，端口 18080）

启动前置：`bash /d/tools/m.sh -P dev -pl jeecg-boot-module/jeecg-boot-module-wms install -DskipTests`（**必须**，见 §6 环境注意）。
登录 `POST /sys/login`（admin/123456，dev 环境无需验证码）取得 token。

| # | 操作 | 实测响应 | 结论 |
| --- | --- | --- | --- |
| 1 | `POST /wms/supplier/add` `SUP-E2E-001` | `code:200 success:true`「添加成功！」 | ✅ |
| 2 | 重复提交同一编码 | `code:500 success:false`「编码已存在，请重新输入」 | ✅ 约束① |
| 3 | `POST /wms/order/add` `PO-E2E-001`（委外订单） | `code:200 success:true`「添加成功！」 | ✅ |

| 5 | `POST /wms/order/audit {pass:true}` | `code:200 success:true`「审核通过！」 | ✅ |
| 6 | 重复审核同一单 | `code:500 success:false`「仅待审核状态的订单可审核」 | ✅ 守卫生效 |
| 7 | `POST /wms/order/dispatch?id=<id>` | `code:200`，`result={"synced":false,"retryCount":3,"syncError":"未配置 ERP/MES 同步地址（wms.sync.erp.url）"}` | ✅ |

说明：
- 步骤 7 的 `success:true` 是刻意的——**下达成功**而**同步失败**，二者分离；前端据 `synced` 字段给黄色警告而非错误，避免用户误判下达也失败了。
- `retryCount=3` 即「首次 1 次 + 重试 3 次 = 最多 4 次调用」；该次调用耗时约 7.2 秒，与退避 1s/2s/4s 吻合（独立旁证）。

## 3. 验收标准② 取证：同步失败的日志与落库

**应用 ERROR 日志原文**（这是验收标准②的直接证据）：

```
2026-10-14 14:53:29.174 [http-nio-18080-exec-4] ERROR
o.j.m.wms.service.impl.WmsOrderSyncServiceImpl:54
- 订单[PO-SMOKE-001]同步 ERP/MES 失败，已重试3次，订单类型=采购订单，供应商ID=null，
  失败原因：未配置 ERP/MES 同步地址（wms.sync.erp.url）
```

含**订单号、订单类型、重试次数、失败原因**四项。

**落库取证**（`GET /wms/order/list` 回读）：`syncStatus=同步失败`、`retryCount=3`、`lastSyncError=未配置 ERP/MES 同步地址（wms.sync.erp.url）`。

**告警取证**：失败时经 `ISysBaseAPI.sendSysAnnouncement` 投站内消息（标题 `WMS订单同步失败告警`，收件人取配置 `wms.sync.alert.to-user`，默认 `admin`）。
本环境无 SQL 客户端，未在 UI 中逐条核对 `sys_announcement` / `sys_announcement_send` 记录，**此项仍为间接证据**。

> **终审曾在此处发现一个 Critical 缺陷（已修，提交 `be59ae17`）**：原实现把收件人 `toUser` 传成 `null`，
> 而平台 `SysBaseApiImpl` 对该值执行 `String[] userIds = userId.split(",")`，null 直接抛 NPE；
> 由于 `insert(announcement)` 在 `split` 之前，结果是**公告落了一行、收件人零条**，异常再被本方法的 try/catch
> 吞成一行日志——**管理员永远收不到告警**。原先的单测只 `verify` 了调用次数（Mock 不会复现 NPE），属假绿。
> 修复后单测改为断言真实收件人/标题/内容。**修复后仍未在 UI 中端到端确认消息可见**（见 §7）。

## 6. 环境注意（后续维护者必读）

1. **Maven 不在 PATH**，必须用 `bash /d/tools/m.sh`。
2. **启动前必须先 install wms 模块**：在子模块目录执行 `spring-boot:run` 时，兄弟模块从 `~/.m2` 解析，
   不是反应堆新产物。漏装会跑**旧包**，表现为「新代码不生效、接口 404、日志查无此类」，而应用启动正常。
   实测过该陷阱（旧包 32,813 字节 → `WmsOrderSyncJobRegistrar` 一次都没出现）。
3. **Flyway 会静默吞错**：迁移失败只留一行 `【数据库升级】flyway执行sql脚本失败` ERROR，应用照常启动。
   验证迁移必须 grep 日志，不能只看「应用起来了」。
4. **8080/8081 已被占用**（8080 为 python.exe）。本报告实测使用 `--server.port=18080`。
5. **Quartz 为集群配置**（JDBC 存储 + `isClustered=true` + 同一 instanceName），而库中还存在另外 3 个既有实例共用
   同一套 `QRTZ_` 表。定时触发器由集群协调，可能被其它节点领走，故**单一实例日志中观察不到每一轮 cron**
   （实测 14:58 那一轮未落在本实例）。这是多实例异构部署的固有现象，非代码缺陷；生产上各节点同版本即无此问题。
   —— 这也是本报告用「立即执行」而非「等 cron」来做自愈取证的原因。

## 9. 结论

验收标准 ①② 均**通过**，并附可复现的命令、响应与日志原文。追加的「同步失败可自愈」需求**通过**。

实现期间发现并修复 **2 个产品缺陷**：
1. 补偿任务缺无参构造器导致「定时任务 → 立即执行」必失败（提交 `6d566edc`）——隐蔽点：正常 cron 路径不受影响；
2. 告警收件人为 null 导致管理员收不到告警（提交 `be59ae17`）——隐蔽点：被只验调用次数的假绿单测掩盖。

两处都不是靠"再看一遍"发现的，而是靠**真跑**（手工触发定时任务）与**独立上下文复审**。

薄弱之处（认领 SQL 无单测、站内消息未端到端核对、前端未在浏览器实操、3 项 Minor）已在 §7 逐条标注，
未以信心替代证据。
