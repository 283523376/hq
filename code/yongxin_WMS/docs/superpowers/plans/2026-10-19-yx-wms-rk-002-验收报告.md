## 4. 与计划/设计的偏差（已在执行台账记录）

| 偏差 | 原因 | 影响 |
|---|---|---|
| 菜单 sort：生产工单=3、生产入库=4 | 既有采购入库=1、检验任务=2 | 仅菜单顺序 |
| `sumInboundedQty` 放在 `WmsProductionInboundMapper` | 汇总读取的是生产入库表 | 无 |
| 同步网关只接收入库记录（不再传工单） | 记录已冗余工单号/物料/批次/数量 | 无 |
| `onContainerLocation` 返回影响行数 | 回调需要区分「容器不存在」 | 回调明细码更准确 |
| 提交校验顺序：工单 → 数量 | 与 spec §7.1.1 一致 | 无 |
| 测试断言改用 `getParamNameValuePairs()` / `getSqlSegment()` | MyBatis-Plus `UpdateWrapper.set(column,value)` 的值不在 `sqlSet` | 仅测试写法 |

## 5. 未覆盖项与遗留风险

1. **真实系统未联调**：MES/ERP 地址、报文最终版、测试账号；堆垛机 WCS 协议与地址；RMS 真实环境的工作站编码、仓库名与回调 URL 注册方式。当前均以空配置占位，配置后即可切换真实链路。
2. **RMS 模拟受理**：`wms.sync.rms.url` 为空时按模拟受理（mocked），真实 RMS 的 `300001/300006/300000` 分支由单测覆盖，尚未对真机验证。
3. **硬件未接入**：RFID 读写器与二维码打印均为操作员扫码录入，未做设备级读写。
4. **成品库存粒度**：WMS 侧按「物料 + 批次 + 敏捷仓在库位」聚合，料箱实际位置由 RMS 管理并回写 `stack_code`；如需按料箱查询库存，下一期需扩展库存模型。
5. **一次提交一个载具**：同一工单大批量需分多次扫码提交；计划量按未关闭记录累计占用。
6. **E2E 演示数据**：运行库中保留了若干 `SC2026...` 生产入库记录与 `WO-DEMO-*` 工单，可作为现场演示数据；如需清空请单独执行。

## 6. 独立代码审查与修复

**审查方式**：独立 opus 审查者读取工作区全部改动（未提交）+ spec/plan，并实测后端 33 个新用例、前端 eslint、运行库迁移与库存数据。结论为 **With fixes**：6 个 Important、24 个 Minor，无 Critical。

**Important 修复（一轮完成，均先写失败测试）**

| # | 问题 | 修复 | 验证 |
|---|---|---|---|
| 1 | 「重新下发」守卫只允许 `待上架`，设备故障转人工后永远无法重下发；Controller 却返回成功 | 守卫改为允许 `待上架/异常待人工` + `未下发/失败`，非法状态抛「当前状态不允许重新下发」；前端按钮条件同步放宽 | `dispatch_fromExceptionAndFailed_redispatches`、`dispatch_invalidState_throws`；API 实测异常单重下发成功、已入库单返回逐字错误 |
| 2 | 下发结果无条件 `updateById`，在途下发可复活已关单记录/覆盖已入库 | 受理与转人工均改为带 `status/task_status` 条件的 UPDATE，影响 0 行不告警 | `dispatch_markManualWhenRecordClosed_noAlert`、受理/转人工条件断言 |
| 3 | 载具只做「先查后插」，跨工单并发可产生两条未完结记录 | 新增 `V3.9.5_14`：生成列 `active_carrier` + 唯一索引；`DuplicateKeyException` 映射「载具正在使用中」 | `submit_duplicateActiveCarrierKey_mapsToUserMessage`；两个工单并发提交同一载具，实测 1 成功 / 1 拒绝 |
| 4 | 料箱位置更新会改写该载具全部历史记录 | `ORDER BY id DESC LIMIT 1` | `containerLocation_updatesStackCode` 断言 LIMIT 1 |
| 5 | 关单释放全部计划量但不良品库存不回滚，重提同一批会重复累计废品 | `sumInboundedQty` 对已关闭记录只计 `bad_qty`（不良品已实际入库，继续占用计划量） | 迁移/接口实测；spec 决策 17 已更新 |
| 6 | 提交同步等待设备下发，最坏约 4 分钟，前端 10 秒超时 | 提交路径改为异步线程池下发；人工重新下发保持同步以返回明确错误 | `dispatchAsync_invokesDispatch`；实测提交 0.246s 返回，3 秒内转「已受理」 |

**复审中发现并一并修复**：FAILED 回执在无状态更新时不再告警（问题 20）；重新下发受理后把状态从「异常待人工」恢复为「待上架」。

**修复后门禁**：wms 模块全量 **515/515** 通过；`V3.9.5_14`、`V3.9.5_15` `success=1`、启动日志 flyway 错误计数 0；后端已重新 install + 重启。
