- 日期：2026-11-02

## 1. 需求

输入单据编号**任意位置的任意连续字符**，查出所有包含该串的单据。
例：搜 `10126` → 命中 `MO1012616533` 等全部含该串的工单。

## 3.5 全局关键词框（2026-11-02 追加）

在 9 个页面的搜索区**首位**新增「全局关键词」框，与原有单字段框**并存**（不替换）：

| 页面 | keyword 覆盖字段 | 实测 |
| --- | --- | --- |
| 物料 | `material_code`、`material_name`、`kingdee_code` | `180` → **972 条** |
| 设备 | `device_code`、`device_name` | `DDJ` → 1 条 |
| 库位 | `location_code` | `R01` → 145 条 |
| 工单 | `work_order_no`、`mes_order_no` | `10126` → 26 条 |
| 生产入库 | `inbound_no`、`work_order_no`、`erp_bill_no` | `1012` → 554 条 |
| 盘点 | `stocktake_no` | 表空，仅编译/单测验证 |
| 审计 | `biz_no`、`biz_ref` | `MO10126` → 2 页 |
| 供应商 / 订单 | 编码+名称+联系人 / 单号+备注 | 已接线 |

**AND 语义验证**：物料 `keyword=180` → 972 条；再加 `materialCode=XA` → **654 条**（缩小，证明是 AND 不是覆盖）。
这依赖「OR 包在 `and(...)` 里」的写法——否则会变成 `status='x' AND a LIKE … OR b LIKE …`，状态过滤直接失效。

**为什么不做成替换**：物料/设备/供应商的编码、名称、规格语义差异大，只剩一个框会让用户
无法「只在编码里搜」，反而更难用。两种框并存，精准和模糊各取所需。

## 4. 明确未改的（设计 §2.2）

- 下拉选择（状态/类型/通道/结果/仓库）——枚举值模糊会串（「已关闭」被「关闭」命中）
- 日期区间
- **按单号取单的内部方法**（`getByWorkOrderNo` / `findByCode` 等）——这些必须精确，否则取错单、破坏幂等

## 5. 已知限制

1. **`%` / `_` 未转义**：用户输入含这两个字符会被当通配符。单号/编码场景基本不出现，本期不处理（设计 §4.1 已声明）。
2. **`LIKE '%x%'` 走不了索引**：物料 4.6 万条实测无明显延迟（1866 条结果秒回）；若将来单表到百万级，再考虑前缀索引或搜索引擎。
3. **盘点页无法实测**：`wms_stocktake_order` 当前为空表，只验证了编译与单测；有数据后应补一次「搜单号部分串命中」。

## 6. 涉及范围外的一点

出库/调拨页用的是 `keyword` 单框搜多字段的模式，体验最好。本期**未**把所有页面统一成这种模式（设计 §4.3 建议本期不做）——用户需求是「能模糊搜到」，不是重构搜索区。
