## 3. 端到端验收抓到并修复的 2 个真缺陷

这两个缺陷**在 313 个单测与前端类型检查下全部绿灯**，只有真库端到端能抓到。它们都不是笔误，是设计层面的错误。

### 缺陷一：唯一索引与逻辑删除语义冲突（三张配置表）

**现象**：`checkCodeExists` 说「编码可用」，保存却撞唯一索引，用户看到的是原始 SQL 异常。

**查因**（真库取证）：
```
SELECT id, warehouse_code, del_flag FROM wms_warehouse WHERE warehouse_code IN ('LB','MJ')
  → 2110568203338735618 | LB | 1        ← 逻辑删除行仍在
SELECT index_name, GROUP_CONCAT(column_name) FROM information_schema.statistics
  WHERE table_name='wms_warehouse' AND index_name='uk_wms_warehouse_code'
  → uk_wms_warehouse_code | warehouse_code   ← 索引不含 del_flag
```

唯一索引只建在业务列上，而实体带 `@TableLogic`。于是：

1. `checkCodeExists` 经 MyBatis-Plus 自动加 `del_flag=0` → **看不见**被逻辑删除的行 → 谎报编码可用；
2. 随后的 INSERT 撞唯一索引 → 用户看到 SQL 异常而非「编码已存在，请重新输入」；
3. 被删除的编码**永久不可复用**；
4. **最要命的一条**：`uk_wms_location_grid`（`warehouse_id,row_no,col_no,layer_no`）同样不含 `del_flag`。库位被逻辑删除后重跑批量生成，那几行会被 `INSERT IGNORE` **静默跳过**（计入 `skipped`）却**不会被恢复**，列表里也看不见 —— **直接破坏「重跑同范围可安全续做」这条承诺，且不留任何痕迹**。

**修法**：三张配置表改为**物理删除**（去掉实体的 `@TableLogic`）。唯一索引与逻辑删除在语义上不可兼得，除非把索引也带上删标记（那样同一编码只能删一次）。这三张是配置表：安全由删除守卫承担（有库位/有设备不许删库区；占用或故障不许删库位），留痕由 `@AutoLog` 的操作日志承担。

配套 `V3.9.5_6__wms_config_hard_delete_purge.sql` 把已有的逻辑删除行真删掉 —— 否则去掉 `@TableLogic` 后它们会「复活」出现在列表里，并继续占着唯一索引。

**回归防护**：`WmsEntityMappingTest.configTables_mustNotUseLogicalDelete`（先看它红再修绿）+ 端到端「附加」四条。

### 缺陷二：编辑库区无法清空维度

**现象**：端到端步骤 18e「清空三个维度」后，生成库位**仍然成功** —— 因为维度压根没被清掉。

**查因**：`editWarehouse` 走 `updateById`，而 MyBatis-Plus 的 `updateById` **跳过 null 字段**。于是「清空维度」返回保存成功而库里纹丝不动 —— 与解绑、清空告警节流是同一类静默故障（那两处我在实现时特意避开了，这一处没避开）。

**修法**：常规字段仍走 `updateById`（漏传字段安全），**三个维度改走 `UpdateWrapper` 显式 set**（null 也要真的写进去）。

**修的过程中又引出一个回归并当场修掉**：第一版把**所有列**都显式 set 了，导致编辑请求漏传 `status` 时抛 `Column 'status' cannot be null` —— 原先 `updateById` 跳过 null，漏传字段本来是安全的。「必须能写 null」（维度）与「null 表示未提供」（其它字段）是两个冲突的要求，故拆成两条语句。

**回归防护**：`editWarehouse_shouldWriteNullDimensionsThroughUpdateWrapper` 与 `editWarehouse_mustNotExplicitlySetNonDimensionColumns`（后者断言 SET 子句**只含三个维度列**，若有人图省事合并回一个大 set 就会红）。

### 4.2 规格 §12 的遗留项（照录）

1. **「占用」依赖未来模块回写**：本期无库存表，`占用` 由谁置位尚无自动化来源；入库模块上线前只能人工设置 —— 这也是增补 `release` 的原因。
2. **`INSERT IGNORE` 会掩盖非重复类错误**（如字段超长）。已用生成前的编码长度校验兜住最可能的一种。
3. **单次 5 万上限 vs 60 万目标**：敏捷仓铺满需 ≥12 次请求，属需求方主动选择的口径；前端已给出超限提示与实时预计数。
4. **告警通道单一**：仅站内消息 + ERROR/WARN 日志，未接钉钉/邮件。
5. **「下发设备注册信息」未实现**：WCS/RMS 接入属 `YX-WMS-SB-002`，当前不存在；接入后应在 `bind` 成功后追加下发调用。
6. **中文字面量枚举**：可读性好，但改文案即等于改数据。
7. **两份同构的 Job 注册器**：刻意不抽象（抽象需改动一个已验收的类，收益约 30 行）。出现第三个任务时再抽基类。
8. **线边柜库区只建档**：其最小存储单元是「格子」，与排-列-层网格不同构；本期可建档但不适用网格生成（由「维度为空则拒绝生成」守卫挡住）。

### 4.3 本次执行新增的遗留项

9. **三张配置表改用物理删除（本次修正）**：`del_flag` 列保留但恒为 0。若将来有「回收站/恢复」需求，需要重新设计 —— 逻辑删除与「编码可复用」不可兼得，要么给唯一索引带删标记并接受「同编码只能删一次」，要么用 `del_flag` 存行 id 并放宽列宽。
10. **`V3.9.5_6` 会真删数据**：它 `DELETE` 掉三张表中 `del_flag=1` 的历史行。生产升级前请确认这些行不需要保留（按本设计的语义，它们本就不可见且不可复用，删除是修正而非丢失）。
11. **编辑库区的契约**：表单必须提交全部三个维度字段；漏传即视为「清空」。当前唯一的调用方（库区编辑弹窗）始终提交三项，但若有新调用方做部分更新，会静默清空维度。
12. **前端页面未经浏览器实测**（见 §4.4）。

### 4.4 前端未做浏览器实测 —— **这条风险后来确实发生了**

`pnpm build`（含 `vue-tsc` 全项目类型检查）通过，证明类型与模块解析无误；但**手写的 .vue 文件从未在浏览器里渲染过**，因此组件挂载期/渲染期错误未在本次执行内被排除。

未做的原因是环境限制：Playwright MCP 固定要 Chrome 渠道，本机只有 Edge、无 playwright 浏览器缓存，补做需在用户机器上下载约 150MB 浏览器 —— 属未经用户同意的系统级副作用，故未做，已向用户提问。

#### 4.4.1 事故实录：整组 wms 页面空白（已在 `bcc972c1` 修复）

用户实测反馈：`/wms/device`、库区与库位，以及**既有的**物料与分类/供应商管理/订单管理**全部空白**。

**定位结论：前端问题，非后端**（菜单能正常拉出 → 登录与菜单接口通；API 级端到端 30/30 通过）。

**根因**：`GenerateModal.vue` 的两个 `computed` 里调用 `getFieldsValue()`，而它在表单注册前返回 `undefined`（实现为 `unref(formRef)?.getFieldsValue()`，`formRef` 未挂载时为 null）→ 解引用 `v.rowFrom` 在**渲染期抛 TypeError** → 打断 Vue 的 patch → vnode/DOM 树不一致 → 之后共享布局里每次 patch 都可能失败 → **连那三个不是本次编写的既有页面也一起空白**。

证据链（dev server 日志，全日志只有两类错误）：
- `TypeError: Cannot read properties of undefined (reading 'rowFrom')`，堆栈帧点名 `GenerateModal.vue:120/128/196`（两个 computed + 渲染）；
- `TypeError: Cannot read properties of null (reading 'parentNode')`，堆栈**全在 Vue 运行时内部**（`patchKeyedChildren` / `processFragment`）—— 是 patch 被打断的**下游后果**，非独立 bug；
- 那三个既有页面**自身零报错**，与「被连带打坏」一致。

**修法（不是补判空 —— 原设计本身也错）**：
1. `getFieldsValue()` **不是响应式的**（内部只是一次函数调用），拿它做 computed 的依赖，预计生成数**永远不会随输入更新**。改用本地 `reactive` 副本，由各字段的 `onUpdate:value` 驱动。选该事件而非 `onChange`，是因为 Vben 的 `FormItem` 把 `onChange` 绑给自己的 `handleFormValuesChange` 且**排在 `componentProps` 之后**（`compAttr = {...propsData, ...on, ...bindValue}`），同名的自定义监听会被覆盖 —— 已读源码确认。
2. 提交前用 `validate()` 返回的**真值**再判一次上限与包络。实时 computed 只是便利，**不该成为唯一防线**。

**同类风险排查**：其余前端文件的 computed 初值全为 `ref(false)`/`ref([])`/`reactive({...undefined})`/`ref({})`，逐个核对无同类隐患；`grep` 确认 `getFieldsValue` 已只存在于注释中。

**这条事故印证了本节原来的判断**：构建通过不等于运行时可用。也印证了代码审查把「前端未实测」列为唯一阻塞项是对的。

#### 4.4.2 浏览器实测已完成（18 / 18 通过）—— 本节原先的空白已补齐

用户批准后装了浏览器，实测方式与结果：

**怎么跑起来的**：Playwright MCP 固定要**系统安装的 Chrome**（`channel=chrome`，路径 `%LOCALAPPDATA%\Google\Chrome\Application\chrome.exe`），而本机只有 Edge，且 Google 的 MSI 与 Playwright 的 CDN 在此网络下均下载失败（`npx playwright install chrome|chromium` 均报 `Download failure`）。**改用 npmmirror 镜像**装成自带 chromium（`PLAYWRIGHT_DOWNLOAD_HOST=https://npmmirror.com/mirrors/playwright/`），再用 `playwright-core` + 显式 `executablePath` 自己驱动 —— **没有改动用户的 MCP 配置，也没有造假 Chrome 路径**。

**登录**：登录页有验证码，但后端 `/sys/login` 不校验（本会话 API 端到端 30/30 即不带验证码登录）。注入 token 到 `TOKEN__` 不被认（Vben 存储带前缀），故**走真实登录表单**、验证码框随便填 —— 这也顺带验证了真实登录路径可用。
