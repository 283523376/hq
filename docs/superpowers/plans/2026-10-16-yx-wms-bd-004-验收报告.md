## 5. 设备阈值真正生效（双向验证）

**正向**（阈值 60 秒）：把 `device.offline.threshold.seconds` 存为 60，令设备 CHG01 心跳滞后 90 秒且状态「在线」，
等一轮扫描任务后：

```
14:22:00.100 WARN WmsDeviceServiceImpl:279 - 设备[CHG01]心跳静默超过 60 秒，已置为离线（最近心跳：14:19:45）
```

**取到的是 60（DB 值），不是 600（常量）**；且该设备滞后 135 秒即被判定离线——旧常量下不会发生。

**反向**（阈值恢复 600 秒）：同样令 CHG01 滞后 90 秒并置「在线」，等一轮扫描后该设备**仍为在线**，
且日志中「超过 60 秒」计数保持 1、无新增——证明阈值确实来自配置且可双向改变行为。

> 「DB 无配置行」时的兜底回落（回到 600）由单测覆盖：`getInt` 在读不到 / 空值 / 非数字 /
> ≤0 / 未知键 五种情况下均返回 fallback 且不抛异常（6 个用例）。

## 6. 执行中发现并修复的问题

1. **纯空白分组会穿过后端参数校验**（Task 7）：`oConvertUtils.isEmpty("  ")` 为 false（该工具不 trim），
   导致 `list?group=%20%20` 抛原始异常文案「未知配置分组：  」而非统一的「参数不识别！」。
   按测试期望修生产代码：`group` / `key` 均 trim 后判空。
2. **服务方法命名与 `IService.save` 重载冲突**（Task 7）：原命名 `save(WmsConfigSaveDTO)` 让所有调用点的
   `any()` 产生编译歧义，且语义上与「保存实体」混淆。改名 `saveGroup`，接口/实现/控制器/测试同步。
3. **`WmsSystemConfigHistory` 若按初稿「不继承 JeecgEntity」会编译不过**（写计划时已发现并修正）：
   `WmsUtils.fillCreate` 的泛型约束是 `T extends JeecgEntity`；因此建表脚本也补了 `update_by/update_time`。

## 7. 验证方法学问题（重要，已修正记忆）

**启动日志是 GBK 编码，中文 `grep` 会静默返回 0 —— 是假阴性。**
本次 `grep -c "flyway执行sql脚本失败" <日志>` 返回 0，但那是**方法不可靠**：文件按 UTF-8 解码直接失败，
按 GBK 解码才是正确文本。改用 GBK 解码复核后确认「flyway执行sql脚本失败」确实为 0、
「数据库版本自动升级」为 1、「心跳静默超过」为 1（即上面第 5 节的设备日志）。

**影响**：任何「grep 中文关键词确认日志没有报错」的做法在本机都不成立——无论如何都应改用
`python -c "open(f,'rb').read().decode('gbk')"` 之后再匹配。该结论已回写进记忆
（`jeecgboot-flyway-swallows-errors`），避免后续会话继续用会静默失败的方法做验证。

全新上下文审查者（最强模型）复核整分支，**无 Critical**；3 个 Important、7 个 Minor。审查者独立复跑 wms 单测确认结论属实。

| 级别 | 发现（均为 UI 可达的真实行为，非理论风险） | 处置 |
| --- | --- | --- |
| Important | **I1** 输入 20 位数字 → `Long.parseLong` 抛 `NumberFormatException` 穿透到 controller 的兜底 catch，用户看到 `For input string: "1000…"` 且**无 conflicts**——「冲突时逐字提示」这条验收点在该输入下不成立 | **已修**：解析加 try/catch，报成普通冲突 |
| Important | **I3** 校验用 `long`、一致性检查与 `getInt` 用 `int`：`min=3000000000` 能存进去但自洽规则按 `0` 漏判（**规则的漏判**）；设备阈值存 30 亿可通过校验，但运行时 `getInt` 溢出回落 600（**页面显示值与实际行为不一致**） | **已修**：INT 统一加 int 上界，超范围即冲突 |
| Important | **I2** 组内有任一键没有上一版本时，回滚把「缺失」判成冲突 → 用户被告知「配置项存在冲突，请检查」但**并无冲突**，且该组在窗口期内无法回滚（与 spec §5.3「跳过并说明」不符） | **已修**：回滚改为校验「回滚后的完整状态」，只写回有上一版本的键 |
| Minor ×7 | `getInt` 的 catch 顺序使「值非法」被报成「键未知」；两条兜底路径未打 WARN；未知 key 抛异常而非冲突；未保存改动的守卫只覆盖页内左侧菜单（刷新/后退仍静默丢失）；`save`/`rollback` 不 trim group；MULTI 允许空元素且不 trim 落库；`getInt` 在告警循环内逐台调用 | **未修**（见 §9 遗留），已逐条记入台账 |

## 9. 遗留与说明

- **7 个 Minor 未修**：按流程 Minor 不进修复轮；逐条清单见执行台账 `progress.md`。
- **验收脚本自身的一处修正**：原 `api-verify.js` 断言「设备离线阈值恰为 600」——该断言依赖**库里有没有配置**，
  是测试数据状态而非代码属性（被 I2 回归脚本回滚成 60 后即失败）。已改为断言「项存在且为可解析正整数」；
  「无配置行时回落默认 600」由单测覆盖（`definitionsShouldFallBackToDefault`、`getInt_shouldFallBackWhenMissing`）。
- 本次为验证阈值人为改动过设备 CHG01 的状态与心跳；结束时其状态为「在线」、心跳滞后，
  下一轮真实扫描（600 秒阈值）会自行置为离线，无需人工干预。
- 测试数据最终状态：库存组 10/50/200、设备组 600/30（已复位）；设备组的历史流水因 I2 回归被清空了一条键的旧记录，
  回滚会产生新的 ROLLBACK 流水，属验证副产物，不影响功能。
- 设计中的两处**有意不做**：配置项元数据不建表（写进枚举）、冲突不做跨组规则——见 spec §0。
