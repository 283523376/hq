# 查询窗口模糊匹配 设计方案

- 日期：2026-11-02
- 状态：待确认
- 需求来源：用户 2026-11-02 提出

---

## 1. 需求

> 「检查一下前端所有的查询窗口，需要将查询窗口做成模糊查询。
> 比如输入单据编号任意位置的任意位字符，就可以查出所有包含这些连续字符的所有单据。
> 例如搜索 `10126` 可以搜到包含 `MO1012616533` 在内所有存在 `10126` 字符串的单据。
> 注意这里的 `10126` 是作为一个连续字符串整体进行模糊查询。」

**一句话**：文本类查询框 = `LIKE '%输入%'`（连续子串，前后都通配），不是精确等值，也不是分词。

## 2. 范围界定（先定清楚，避免误改）

### 2.1 要改的

**列表页搜索区的文本输入框**，且当前是精确匹配（`eq`）的字段。

### 2.2 不改的（重要）

| 类型 | 理由 |
| --- | --- |
| 下拉选择（状态/类型/通道/结果/仓库…） | 枚举值，精确匹配是正确语义，模糊反而会串（如「已关闭」被「关闭」命中） |
| 日期区间 | 区间语义，不适用 |
| **按单号取单条记录的内部方法**（`getByWorkOrderNo`、`findByCode`、`getByMaterialCode` 等） | 这些是业务主键查找，必须是精确匹配；改成 like 会取错单、拖慢、甚至改变幂等语义 |
| 扫码/设备回调等机器入口 | 上游传的是精确编码 |

> 这条边界是本方案最容易出事的地方：`work_order_no` 在「列表查询」里要 like，在「按单号取单」里必须 eq。两者不能一刀切。

## 3. 现状盘点（2026-11-02 实测确认）

前端查询窗口共 **11 个 `*.data.ts`（searchFormSchema）+ 若干 index.vue 内联 formConfig**。
用真实接口逐页实测（搜部分子串看是否命中），结论按实现方式分成两类：

### 3.1 已经是模糊的（手写 LambdaQueryWrapper + `like`）

| --- | --- | --- |
| 生产工单 | `workOrderNo` | 搜 `10126` → 26 条、搜 `16533` → 1 条（尾部子串命中）✅ |
| 生产入库 | `inboundNo` | 搜 `650919` → 1 条 ✅ |
| 出库 | `keyword`（单号/工单/销售单/客户） | 搜 `1012` → 3 条 ✅ |
| 调拨 | `keyword`（4 字段） | 代码为 `like`（表空无法实测） |
| 审计日志 | `bizNo` | 代码为 `like` |

### 3.2 是精确匹配的（Jeecg `QueryGenerator` + 实体参数）

## 4. 方案

### 4.1 后端（唯一的语义来源）

列表查询里，文本类字段统一 `wrapper.like(column, value.trim())`。

`like` 生成的是 `column LIKE '%值%'` —— MySQL 默认行为，**天然满足「连续子串」语义**，无需额外处理。

**注意三个坑**：

1. **不要额外加 `%`**：MyBatis-Plus 的 `like()` 已经会包 `%`，手写 `"%" + v + "%"` 会变成 `%%v%%`（语义相同但索引更差），也会让人误判。
2. **转义 `%` 和 `_`**：用户输入如果含这两个字符，会被当成通配符。需要转义或至少接受（单号场景几乎不会出现，但 spec 要写明取舍）。
3. **空值不拼条件**：现有代码已有 `oConvertUtils.isNotEmpty` 守卫，改造时保留。

### 4.2 前端

多数页面无需改动（参数名不变，只改后端语义）。

**例外**：目前「关键词」类页面（出库/调拨）用一个 `keyword` 同时 like 多个字段，这是好模式，可保持；单字段页面继续用各自字段名。

前端**不加**任何过滤逻辑——模糊匹配是后端职责，前端只传原值。

### 4.3 全局关键词框（2026-11-02 拍板：做）

**做法：不替换，只增加**。各页保留现有单字段框，另在搜索区首位加一个「全局关键词」框，
两种能力并存：

- 想精准 → 用具体字段框（如「物料编码」）
- 想跨字段模糊 → 用「全局关键词」，一次搜多个单号/名称字段

**为什么不做成替换**：字段语义差异大的页面（物料/设备/供应商）如果只剩一个关键词框，
用户无法限定「只在编码里搜」，反而更难用。

#### 各页 keyword 覆盖字段

| 页面 | 全局关键词覆盖的字段 | 说明 |
| --- | --- | --- |
| 生产工单 | `work_order_no`、`mes_order_no` | 两个号常被混用 |
| 生产入库 | `inbound_no`、`work_order_no`、`erp_bill_no` | WMS 单号 + 工单号 + 金蝶单号 |
| 出库 | 已有（`outbound_no`/`work_order_no`/`sales_order_no`/`customer_name`） | 不动 |
| 调拨 | 已有（`transfer_no`/`erp_bill_no`/出库仓/入库仓） | 不动 |
| 盘点 | `stocktake_no` | 单号 |
| 物料 | `material_code`、`material_name`、`kingdee_code` | **不含规格/单位**：语义差异太大，纳入只会制造噪音 |
| 设备 | `device_code`、`device_name` | |
| 供应商 | `supplier_code`、`supplier_name`、`contact` | |
| 库位 | `location_code` | |
| 订单 | `order_no`、`remark` | |
| 审计日志 | `biz_no`、`biz_ref` | **不含 operator/error_msg**：会捞出无关记录 |

#### 实现约束

1. **OR 必须包在一个 `and(...)` 里**，否则会与其它字段条件串成
   `status = 'x' AND a LIKE … OR b LIKE …`，优先级错误导致状态过滤失效。
2. keyword 为空时**不拼任何条件**（沿用 `oConvertUtils.isNotEmpty` 守卫）。
3. 前端字段名统一 `keyword`，label 统一「全局关键词」，放在搜索区第一位。
4. keyword 与单字段框**同时填写时是 AND 关系**（更精确），这是预期行为。

## 5. 验收标准

每条都要**实测**，不接受「代码看着像 like」：

1. **连续子串命中**：在工单页搜 `10126`，能查出 `MO1012616533`、`MO1012615790` 等全部含该串的工单
2. **不误伤**：搜 `10126` 不会查出 `MO1012600019`（不含该连续串）
3. **前后通配**：搜 `16533` 能命中 `MO1012616533`（尾部子串）；搜 `MO10` 能命中（头部）
4. **跨页一致**：工单/入库/出库/调拨/盘点/物料/设备/供应商/库位/订单/审计，逐页用同一串测试
5. **下拉不受影响**：状态下拉仍精确（选「已关闭」不返回「已作废」）
6. **内部查找不受影响**：按单号同步、回写、幂等等原有单测全绿（1156 条基线）

## 6. 风险

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **误改内部精确查找** | 把 `getByWorkOrderNo` 改成 like → 取错单、幂等失效 | 改造只碰列表查询方法；内部方法用单测锚定 |
| 索引失效 | `LIKE '%x%'` 无法走索引，大表变慢 | 单号/编码字段数据量可控；若后续变慢，再考虑前缀索引或 ES |
| `%`/`_` 输入 | 用户输入含通配符会被解释 | 本期不做转义（单号不含该字符），写进限制 |
| 下拉被误改 | 状态模糊匹配会串值 | 明确列为「不改」清单 |
