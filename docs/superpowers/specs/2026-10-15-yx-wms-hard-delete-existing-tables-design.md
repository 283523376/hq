# 既有 4 张业务表「逻辑删除 × 唯一索引」缺陷修复 — 立项说明

- 日期：2026-10-15
- 类型：既有缺陷修复（非新功能）
- 触发：BD-003 端到端验收修复了**同样缺陷**在 3 张新表上的实例后，回查发现既有 4 张表是同一个坑
- 状态：待评审

---

## 1. 问题

BD-003 期间发现并修复了一类缺陷：**唯一索引只建在业务编码列上、不含 `del_flag`，而实体带 `@TableLogic`**。
两者语义不可兼得，表现为三条静默故障。修复后回查既有表，**同一个坑在这 4 张表上原样存在**：

| 表 | 唯一索引（真库已核） | 实体 |
| --- | --- | --- |
| `wms_material` | `uk_wms_material_code (material_code)` | `WmsMaterial` |
| `wms_material_category` | `uk_wms_mat_cat_code (category_code)` | `WmsMaterialCategory` |
| `wms_supplier` | `uk_wms_supplier_code (supplier_code)` | `WmsSupplier` |
| `wms_order` | `uk_wms_order_no (order_no)` | `WmsOrder` |

（四者均带 `@TableLogic`，`@TableLogic` 与索引定义均已用真库 + 源码核实，非推测。）

### 1.1 三条静默故障

以「删除供应商 `SUP001` 后想重新建一个 `SUP001`」为例：

1. **查重与保存的结论互相矛盾**：`checkCodeExists` 经 MyBatis-Plus 自动加 `del_flag=0`，**看不见**被逻辑删除的那行 → 回答「编码可用」；随后 `INSERT` 撞唯一索引 →抛 `Duplicate entry` 的**原始 SQL 异常**，而不是「编码已存在，请重新输入」。
2. **被删除的编码永久不可复用**，且没有任何显式原因提示。
3. **对 `wms_material_category` 额外多一层不一致**：删除守卫是「该分类下存在物料或子分类则拒绝」，而这两个计数都用 `this.count(...)`（走 MyBatis-Plus，会被自动加 `del_flag=0`）。因此守卫**看不见已逻辑删除的行** —— 它的判断依据与数据库里的实际占用不一致。
   > **准确表述**：这**不是**「绕过守卫导致误删」级别的问题 —— 被逻辑删除的子分类本就已不可见，删掉它已删的父分类不算误删。它的实际危害仍落在第 1、2 条（已删行的编码继续占用、查重与保存结论矛盾）。之所以单列，是因为它说明**同一个根因还污染了业务判断的依据**，不止污染报错文案。

### 1.2 影响面（按表）

| 表 | 用户可感知的后果 | 严重度 |
| --- | --- | --- |
| `wms_material_category` | 除第 1、2 条外，守卫计数忽略已删行 → 判断依据与库内实际不一致（见 1.1-3） | 中高 |
| `wms_material` / `wms_supplier` | 编码永久不可复用 + 报错信息是 SQL 原文而非业务提示 | 中 |
| `wms_order` | 同上；订单号是业务主键，重号再建是常见操作 | 中 |

> 说明：这些是**既有缺陷**，不是 BD-003 引入的。BD-003 只改了它自己新增的 3 张表。

## 2. 修法

**与 BD-003 已验证的方案完全一致**，不引入第二种解法：

1. **去掉 4 个实体的 `@TableLogic`**（`delFlag` 字段与列保留，恒为 0）→ 删除变为**物理删除**。
   - 删除入口（`removeMaterial` / `removeBatch` / `removeSupplier` / `removeOrder` / `removeCategory`）**全部无需改动** —— 它们已经用的是 `removeById`/`removeByIds`，注解移除后自动落成 `DELETE`。
2. **Flyway 迁移清理已存在的逻辑删除行**（`del_flag = 1`）—— 否则去掉注解后它们会「复活」出现在列表里，并继续占着唯一索引。
3. **扩展回归防护**：把 `WmsEntityMappingTest.configTables_mustNotUseLogicalDelete` 的断言从 3 张表扩到 7 张表 —— 谁再把 `@TableLogic` 加回来，测试立刻红。

### 2.1 为什么选物理删除，而不是「索引带上 del_flag」

| 方案 | 问题 |
| --- | --- |
| 索引改为 `(code, del_flag)` | 同一编码**只能删一次**（第二次删除的两行 `del_flag` 都是 1，仍撞索引）；且 `@TableLogic` 的删值是固定的 0/1，做不到「每行一个唯一删值」 |
| `del_flag` 存行 id、放宽列宽 | 需要改列类型 + 自定义删除逻辑，改动面远大于收益；且仍要处理守卫计数 |
| **物理删除（选定）** | 两个唯一索引立刻名副其实 —— 编码只被**现存记录**占用；守卫计数也不再有「看不见已删行」的偏差 |

安全性与留痕的替代保障（与 BD-003 相同的论证）：

- `wms_material_category` / `wms_order` 已有**删除守卫**（有物料/子分类拒绝；非待审核或已驳回拒绝）；
- 所有删除接口都带 `@AutoLog`，**留痕在操作日志**里，不在被删行上；
- 这 4 张表都是**主数据/配置类**，重建成本低。

### 2.2 明确不改的东西

| 不改 | 原因 |
| --- | --- |
| `WmsOrderMapper.xml` 里的两处 `del_flag = 0` | 属 BD-002 的**认领/扫描 SQL**（最敏感的部分），且两种删除语义下都正确（物理删除后该条件恒真） |
| `wms_material` / `wms_supplier` 的删除守卫 | 本次不新增守卫 —— 那是**功能范围扩张**，不是缺陷修复。若需要应另行立项 |
| `wms_order` 与供应商的关联方式 | `wms_order.supplier_id` 无外键；供应商被删后订单查不到供应商名 —— **现行逻辑删除下已经是这个行为**（`selectBatchIds` 自动过滤 `del_flag=0`），本次不产生变化 |

## 3. 验收标准

| # | 标准 | 验证方式 |
| --- | --- | --- |
| ① | 4 张表同一编码**删除后可复用** | 真库端到端：建 → 删 → 用同编码再建，必须成功 |
| ② | 删后重号时，**查重接口与保存结论一致** | 查重返回「可用」，保存成功（而不是一个说可用、一个抛 SQL 异常） |
| ③ | `wms_material_category` 的守卫计数与库内实际一致 | 真库端到端：子分类被删除后，父分类的「有子分类」守卫判断与库内实际行数一致（物理删除后二者必然一致） |
| ④ | 既有 4 个功能**无回归** | 全模块测试（315 个）保持全绿 |
| ⑤ | 无人再把 `@TableLogic` 加回来 | `WmsEntityMappingTest` 断言覆盖 7 张表 |
| ⑥ | 迁移幂等、且**明确标注会真删数据** | 脚本用 `DELETE ... WHERE del_flag = 1`；在脚本头部与验收报告中显著说明 |

**明确非目标**：为 material / supplier 新增删除守卫；引入「回收站/恢复」能力；改动订单与供应商的关联模型。

## 4. 风险与遗留

1. **迁移会真删数据**：`V3.9.5_8` 会 `DELETE` 这 4 张表中 `del_flag = 1` 的行。按新语义这些行本就不可见且不可复用，删除是修正而非丢失；但**生产升级前需确认这些行不需要保留**。
2. **失去「恢复」能力**：与 BD-003 的取舍一致。若将来要回收站，需重新设计（见 §2.1 首行：逻辑删除与「编码可复用」不可兼得）。
3. **`wms_material` / `wms_supplier` 无删除守卫**：物理删除后误删即不可恢复。当前**没有比之前更危险**（逻辑删除下它们也一样查不到、也被唯一索引占着），但这是一条应当在后续立项中补齐的防护。
4. **`WmsOrderServiceImpl` 里一条注释会变陈旧**（提到 `selectBatchIds` 自动带 `del_flag=0`），随本次一并订正。
